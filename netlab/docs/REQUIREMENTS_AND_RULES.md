## 1. 本版改了什么

1. 你 2026-10-25 提出的七大块新要求（模块化文件化、前端信息架构、场景重组、快捷键、多网络、连线与符号、时间与循环）全部并入，旧七项需求被**细化或取代**，映射见 §7。
2. 新增三条你点名的横切要求：**数据依赖与数据保护**、**性能与计时**、**现代控制理论导向（仅呈现层）**。
3. 所有决策从问答沉淀成 **D1–D59 台账**，每个决定都能追到当时的取舍。
4. 计划从旧的 V2-0…V2-7 改为 **P0–P6**，并明确：P0 是地基（数据模型 + 目录 + 菜单 + 交互基础）先做，且含一个**热修**（现网报错）。
5. 新增 §6「不做清单」——把"以后再说"和"明确不做"分开写清，避免下个窗口又把它们当需求实现。

## 8. 横切约束：数据依赖与数据保护

1. **单一写入口**：所有落盘经 `atomic_write`（临时文件 → fsync → `.bak` → 替换）+ 校验和。
2. **引用可见**：跨文件依赖（工程→库模块、工程→扩展、网络→网络）必须有显式索引；删除/改名/覆盖前先扫描并列出受影响对象。
3. **只读共享**：`library/` 内模块默认只读；修改唯一路径是"另存为副本"或"导入新版本"。
4. **不覆盖**：导出同名自动加时间戳/序号；自动保存只写 `backups/`，绝不覆盖正本。
5. **失败即停**：缺失/损坏/校验失败 → 禁用运行并给可执行的修复动作，绝不带假数据继续算。
6. **可复现**：工程记录模块版本、线性化点、分析窗口；换机器打开能得到同一结论（文档与代码同版本打包）。

所有新增和修改代码都必须遵循现有项目规范，并根据实际语言与工具采用合适的质量要求。

对于 Python 代码：

使用明确、统一的命名规则和必要的类型标注。

为核心类、公共接口及复杂算法提供适量的文档字符串和注释。

让每个模块、类和函数具有明确职责，避免循环依赖和过度耦合。

合理使用异常类型，不能用宽泛的异常捕获掩盖错误。

不使用隐式共享可变状态作为跨模块通信的默认方式。

避免不必要的动态导入、全局变量和重复实现。

对关键的数据结构、边界条件和数值算法编写针对性测试。

遵循项目已有格式化工具、类型检查器和静态检查规则；没有现有工具时，先评估必要性，避免无故增加依赖。

对于前端和桌面端代码，也应遵循现有组件结构、状态管理、事件处理、样式规范和接口约定，不因局部 UI 需求而重复实现整套业务逻辑。

任何重大架构变化都必须先说明原因、替代方案、改动范围、兼容性、风险和验证方法。

十二、强制执行的防死循环机制

这是必须遵循的规则，不得为了完成任务而忽略。

先复现问题或找到明确证据，再实施修复。无法复现的问题应标记为未确认。

对同一根因最多进行两轮有实质区别的修复尝试。每次尝试必须说明变化点，以及为什么预期能够解决问题。

若第二轮仍失败、错误没有变化，或出现更多相同错误，立即停止自动修复，汇总已尝试方案、命令、实际错误和可能原因。

同一失败命令没有新证据时不得反复运行。重复测试仅用于验证确实发生了修改、环境状态改变或需要确认结果的情况。

环境依赖缺失、权限限制、网络异常、API 余额不足和第三方服务故障，应与代码错误分开诊断。

不允许通过不断修改无关代码、扩大重构范围、关闭检查或删除测试来规避问题。

如果测试预计耗时过长，应先执行最小必要测试集，再逐步扩大测试范围。

若多个问题相互独立，先解决当前阶段的阻塞问题，不得在一个错误上无休止地消耗资源。

对无法处理的问题保留有价值的诊断结果，给出最小复现方式和人工处理建议。

不进行没有依据的反复规划、重复总结、重复读取相同文件或冗长的过程性输出。

十三、阶段计划、任务优先级与实施规则

在完成首次调查后，根据现有代码、模块依赖和真实风险制定合理的分阶段计划。不得未经调查就固定所有功能的先后顺序。

计划必须涵盖上述七类需求，并为每个阶段明确：

阶段编号和目标。

前置条件及依赖。

涉及的模块和预计修改的文件。

明确不包含的任务。

关键技术决策和采用理由。

交付物及验收标准。

测试命令和验证方法。

性能基准或数值正确性基准（适用时）。

数据迁移、兼容性、安全风险和本地恢复方案。

优先选择能够尽早验证核心架构、计算正确性和数据安全的最小可运行闭环。避免同时重构计算内核、桌面界面、存储格式和所有元件。

每个阶段必须先建立清楚的完成条件。阶段规模应以能够独立实现和验证为准，而不是机械地限定文件数量或代码行数。

十四、测试、审查与阶段完成标准

开发时首先检查已有测试和执行方式，不要假设命令、模块或依赖名称。

每个阶段根据实际变化执行适当的验证：

相关单元测试。

集成测试及必要的回归测试。

静态检查、类型检查或格式检查（如项目已有相应工具）。

构建、启动或应用实际操作验证。

对性能敏感的任务执行可重复基准测试。

对求解器、矩阵运算和元件行为执行数值正确性验证。

检查本阶段全部验收条件和实际修改文件。

代码实现完成后，另行执行一次独立审查。审查应检查实际文件内容和本地变更记录，不依赖 Git。重点检查功能正确性、架构一致性、数据安全、计算顺序、资源生命周期、错误处理、兼容性、测试覆盖和无关改动。

如果条件允许，可以使用另一轮独立审查任务或不同模型进行审查，但不得为了并行而使多个执行者同时修改同一批文件。

只有当本阶段所有必须验收条件均得到验证时，才可标记为通过。部分完成或存在失败条件时，必须如实报告。

十五、文档与进度管理

首次调查阶段不修改任何文档。获得开发阶段批准后，再根据实际工作更新已有文档；不要无故创建重复或相互冲突的文档。

如果项目尚无适当的进度文件，可在批准后创建 docs/progress.md，用来记录：

当前阶段及状态。

已完成和未完成的任务。

实际修改的文件。

执行过的测试命令和真实结果。

已确认的问题和已知限制。

重要接口或架构变化。

本地备份位置。

下一阶段建议。

重要架构决策应简洁地记录方案、原因、备选方案及影响。尽量增量更新现有文档，不要每次重新生成整份 ARCHITECTURE.md 或 EXTENDING.md。
